How it works

Time zones

Everything is stored, entered and displayed in UTC. The header shows a live UTC clock next to your browser's clock. The catch-window inputs show what each UTC time is in your local time zone, so you can spot a wrong time zone before saving.

Monitoring

Every domain has its own worker, so a slow registry or a long drop-catch on one domain never delays another. Each worker checks at the domain's own interval, or the faster "armed" interval while drop-catch is armed.

  1. WHOIS/RDAP (the whois-domain-lookup sidecar) is the primary source. It reports availability plus registrar, dates, EPP status and nameservers. An empty or unparseable answer is never treated as "available".
  2. When the internal WHOIS sidecar fails or is rate-limited for a suffix, the check goes to the external WHOIS sidecars (EXTERNAL_WHOIS_API_ENDPOINTS: the same program on other servers, so other IPs and rate-limit budgets), in order. Only when all of them fail does it fall back to Cloudean and Regery (keyless web checkers), then to the availability APIs of configured registrars. Availability APIs never place orders.
  3. Every answer updates a per-suffix health record. A source that is rate-limited, or fails several times in a row, is benched for that suffix and retried after a cooldown. A source that says it doesn't sell a suffix is skipped for a week. WHOIS returns as primary as soon as it answers again. See Sources.

Drop-catch

A domain is armed when it has at least one registrar selected and either:

  • drop-catch is switched on and the current UTC time is inside its optional window, or
  • "auto drop-catch on pending delete" is on and a pending delete status has been seen.

While armed, the domain is checked at the faster interval, and its WHOIS requests jump the per-suffix queue. On the first "available" signal from any source, orders go out to all selected registrars at the same time, each at its own documented pace. Orders are retried until one of these happens:

  • a registrar reports success (won);
  • a registrar accepts the order asynchronously (pending): that registrar is not ordered again;
  • the master monitor sees the domain registered twice in a row (someone else got it: lost);
  • the "keep placing orders for" duration or the catch window ends;
  • you press stop.

Registrar errors that retrying can't fix (bad keys, insufficient balance, unsupported suffix, premium name, missing contact) drop that registrar from the session and log a warning. Registrars only receive orders during a session. Availability is decided by the monitor, so no order calls are spent on routine checks.

Set ORDERS_DRY_RUN=true in .env to rehearse: sessions run and log everything, but nothing is bought. Porkbun uses its official dryRun option, which also confirms the price.

Scheduled fire

For registries that release domains at a fixed time (the .tw rule, for .tw and all .xx.tw: 06:00:00 UTC on the 33rd day after the expiry date in Taiwan time; the .ca rule: CIRA's To-Be-Released session, Wednesdays 19:00:00 UTC, the same week if the domain turned pending delete before Monday 07:00 UTC, else the next week. the date is taken from CIRA's published TBR list, fetched hourly, and computed only for domains not on it yet), a domain can carry a fire time. From lead seconds before it until duration minutes after it, orders go to every selected registrar without checking availability, because registry data seen through WHOIS/RDAP can lag by hours. Set it on the domain page: either by hand (UTC) or "use the release rule", which recomputes it whenever the registry data changes and applies the rule's default lead and duration. It fires once per fire time, and only while drop-catch is on.

Fresh registry data

Registry answers can come from old copies (TWNIC RDAP replicas lag up to hours). Each answer passes a freshness guard: answers from an older registry snapshot, with older creation/expiry dates, or predating the current state are ignored; a status change needs 2 agreeing answers unless it is self-evident (direct port-43 answer, new delegation in the zone, newer registration). Orders still start on the first plausible "available". The domain page lists every raw answer with its timing and verdict under Registry answers; only real changes appear in Events. Around an expected release the monitor polls fast (.tw: every second 05:55-06:10 UTC; .lu: every 1-2 min on the End Date).

.lu rule: no fixed drop time. After 30 days of quarantine (ACTIVE (PENDING_DELETE)) domains are deleted one at a time in quarantine order, at any hour (samples: 03:51 to 20:16 UTC, 40 min to 16 h apart). The estimate is quarantine entry + 30 days (or expiry + 30 days as an upper bound); the domain is watched from a day before to a day after it, alternating a registrar/web check every 45 s with WHOIS every 90 s, and orders start on the first "available". Availability is confirmed by two independent checks incl. a registrar API even while WHOIS still shows pending delete (it lagged 15-32 min).

Notifications

Telegram messages and Twilio calls are per-domain switches. To avoid false alarms from unstable registries, the admin is notified only when availability is confirmed: WHOIS/RDAP says available and at least one of Cloudean, Regery or a registrar API that supports the suffix agrees. Each availability episode is notified once. Orders start before confirmation, because speed matters more there.

Optionally (Settings → "Confirm without WHOIS"), suffixes that WHOIS can't answer can be confirmed by two independent fallback sources instead.

Registrar support per suffix

No single registrar sells every suffix. When a domain is added, the price database is queried: nazhumi first, which lists every registrar for the suffix, with miqingju as the fallback. The domain page then marks which of your registrars sell that suffix, and at what price. Data is cached for a day.
